# API

- Run a decision that guards a write inside one `database.transaction`, together with its reads and its write, in this shape: read, then pass what you read to the Core decision, then handle its Outcome with one exhaustive `Match.valueTags`. Each success branch calls the one Repository method that does its whole write, such as `routineRepository.create({ input, userId })`, or returns `Effect.void` when the success writes nothing, and every broken rule fails with `Effect.fail`, which rolls the transaction back. Never branch with an early `if`, because only `Match` fails to compile when a new Outcome isn't handled.
- Give each write its own Repository method, which runs every query of that write, and never compose a write from several Repository calls or a private write function in the Application Service, so every write sits behind the Repository and the Application Service reads as its decision.
- Lock with `FOR UPDATE` the rows that the write changes, and leave unlocked a read that only checks that a row exists, so two concurrent writes can't both decide on the same stale read, while the other reads block no unrelated transaction.
- Make a write filter only by the ids of the rows it changes, and never repeat in SQL a check that the Core made on rows the transaction locked, such as who owns the Routine, because a second copy of a rule drifts from the first.
- Write a create as a plain `insert`, never as an upsert, so every row a write changes is one the Core decided on: the Core decides a create when no row has the id, and the update half of an upsert would change a row the Core never read.
- When a unique index enforces a rule, make the Repository method that writes turn the index's violation into the rule's Wire error, because the index is what catches two requests that race, and an unmapped violation reaches the User as an internal error. A primary key keeps the id of a create free: its violation means that a row the Core never read took the id, so handle it as the Shell handles the Outcome that the Core gives for a row the User can't reach, usually the not-found Wire error, and the response never tells that the id exists.
- Give an Application Service method that acts for the signed-in User a `userId` key, and pass it `ctx.session.user.id` from the procedure, because the Application Service is built once when the Runtime starts and can't read a request's session.
- The tRPC error formatter hides the message of every error of 500 and above, as the server's Fastify error handler does, so when you change what one of them hides, change the other in the same change.
